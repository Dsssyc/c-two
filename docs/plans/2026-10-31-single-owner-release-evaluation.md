# 单一属主释放方案评估

日期：2026-10-31。输入：upstream main `606b8f13`。起因：[跨进程释放调研](2026-10-31-cross-process-release-survey.md)第四节的长期方向，以及[过度防御复审](2026-10-31-over-defense-review.md)中的 R07。状态：评估，没有改动代码；是否采用、何时实施，待用户决定。

## 结论

方案更干净，开销可以忽略，建议作为协议批的核心方案。所有权与进程边界一致：每个分配器只有属主一个进程在写，"别的进程持锁时被挂起或死掉"这类失效从根上不存在；判断对端是否还在只看连接的生命周期，不再需要 PID、超时和毒化标记。主要代价有两项：hold 的生命周期要和连接绑在一起，这是公开语义的调整；以及一次横跨 Rust、Python、Node 的协议、SHM 格式与 C ABI 变更。

## 现状（Host 核对）

- 服务端每个进程一个响应池，所有连接共用（`c2-server/src/server.rs:593`）。客户端读完或释放 hold 时，经自己映射的段直接在服务端的池里释放（`c2-ipc/src/client.rs:537` 的 `free_at`），走段头里的跨进程分配器锁。
- 请求池每条连接一个，归 IpcClient 所有。服务端在 Core 里先把请求拷进自有缓冲（`c2-core/src/host.rs:1246`），保留传输租约到 invoke 返回，再在客户端的池里直接释放。
- dedicated 段靠段头的 `read_done` 标志与崩溃超时回收（`c2-mem/src/pool.rs:494-540`）。
- held 响应能跨重连存活：每次握手换新的池容器，保留的回复留着旧容器（`c2-ipc/src/client.rs:3349`），释放仍直接写进服务端的池。
- 客户端拿到 SHM 响应、还没释放就死掉时，那块 buddy 内存一直占在服务端的池里，直到服务端退出；dedicated 段有崩溃超时，buddy 段没有。Host 检索 c2-mem、c2-server 与 c2-ipc，没有找到按连接或按进程回收的机制。

## 方案草图

1. **释放即消息。** 持有方不再写别人的分配器，而是把释放记录（段号、代际、偏移、allocation_id，约 24–32 字节）交给属主：捎带在下一个出站帧上，空闲时攒批单独发一次。属主在自己进程里释放，并在这一处校验记录，因为它来自另一个进程，是真实边界。
2. **请求块由客户端自己释放。** 响应帧（包括错误回复）本身就表明服务端已用完这个请求，这与现在"Core 保留传输租约到 invoke 返回"的顺序一致；客户端收到后释放自己的请求块，不需要新消息。客户端在仍有已派发请求时关闭连接，沿用现在的做法：放弃整个请求池、不再复用，服务端的映射在它解除之前一直有效。
3. **连接即租约。** 属主按连接记下借出的块，对端关闭它那一端之后，回收该连接名下的块；对端进程退出时由操作系统关闭。属主不主动关闭仍有借出块的连接：判定对端冻结时只停止服务、保留套接字，直到对端退出。客户端在仍有 hold 时保留连接（hold 持有连接的引用），关闭前先使 FastDB 视图失效。
4. **分配器回到进程内。** 段头只留几何信息，跨进程锁字、PID、死亡观察与毒化标记随之删除；释放记录的身份校验用属主进程内的记录完成。

## 评估要回答的五个问题

**1. 消息开销：可以忽略。** 本机（macOS 27）实测：Unix 流上一条 32 字节单向消息每条约 1.1 µs，16 条一批时每条约 50 ns，往返约 4.3 µs。SHM 只用于 4 KiB 以上的载荷；即使每次响应都单独发一条释放消息，也只增加约 1 µs；作为参照，R15 记录中 128 B 原生 RPC 的 P50 约 42 µs，而走 SHM 的调用载荷更大、耗时更长，增量不到 3%。捎带或攒批后约 50 ns。现在的直接释放也要在共享段上做原子操作和位图更新，估计量级相当，但没有单独实测。

**2. 请求块由谁释放：客户端自己，在收到响应时。** 见草图第 2 条，不新增消息。

**3. 断线时的 hold：用"连接即租约"，三种断开都安全。** 客户端主动关闭时，它先使视图失效再关；对端进程死亡时，已经没有人会读；服务端判定对端冻结时，不关连接、不回收，等对端退出。服务端进程死掉时，客户端已映射的内存仍然有效，hold 可以继续读，释放成了空操作。代价有两项：冻结对端的套接字与借出块要一直留到它退出；hold 不再能"在连接关闭后单独存活"，现在 retained replies 跨重连保留旧池容器的能力，改为"hold 未释放时连接保持打开"。也考虑过每条连接一个响应池、断开时整池放弃，这样同样安全，但段数随连接数成倍增长，不采用。

**4. 协议与 ABI：一次集中变更。** 握手版本 15（释放记录与借出边界），SHM 格式 4（段头去掉跨进程字段），C/FFI ABI 7（Node 的释放改走连接）。并入复审第五节的协议批，Rust、Python、Node 一起改，按 AGENTS.md 用确切候选跑全平台门禁。

**5. 顺序：先定本方案，再动相关项。** 采用后，下列改造都不再需要：R07 的改进版、A7 毒化标记、A 区"持锁者已死时重复自旋"、C2 dedicated 退休执行器、dedicated 的 `read_done` 与崩溃超时，以及 C-U1 中为了不在分配器锁上阻塞所做的部分；A1 的位图扫描随分配器进程内化一并消失。真缺陷批与死代码批与本方案无关，可以先做。

## 可删与新增

可删：分配器锁的 PID 锁字、死亡观察与毒化；R07 在 c2-mem、Core、Held 与 Python 中的保留与重试；dedicated 的 `read_done` 与崩溃超时回收；C2 退休执行器；C-U1 结算层的大部分；段头 v3 的跨进程字段。新增：释放记录的编码与校验，属主按连接的借出表与 EOF 回收，出站帧捎带与空闲攒批，客户端"有 hold 不关连接"的引用。删除量明显大于新增，具体行数在出详细方案时核算。

## 需要用户决定

1. 是否采用这个方向，作为协议批的核心。
2. hold 的生命周期改为与连接绑定：hold 未释放时连接保持打开，连接关闭前视图先失效。
3. 判定冻结的对端不再被关闭连接，只停止服务，它的借出块留到它退出。

采用后的下一步是出详细设计：消息格式、借出表、捎带与攒批的时机、各种断开路径的失败场景与验收计划，经用户批准再实施。
